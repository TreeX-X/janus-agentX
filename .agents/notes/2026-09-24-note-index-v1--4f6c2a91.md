# Lightweight Note index v1

## Problem

The file scan already resolves Note IDs, parses documents, calculates source hashes, and reports invalid files. Consumers still need to rescan or reimplement graph logic to answer backlinks, relation filters, code-reference queries, and simple body search. A committed index or a search database would add a second source of truth for a capability that can be derived from the Note files.

## Decision

`buildNoteIndex` keeps the file scan as the only source of truth and derives `byUri`, outgoing edges, complete declared relations, and incoming backlinks in the same pass. Parent links are represented as `parent` edges alongside frontmatter relations. `queryNoteIndex` provides small metadata, relation-type, code-path, and substring filters. `searchNoteIndex` provides bounded deterministic substring search across title, metadata, body, code references, and relations, with title and code-reference matches ranked above body matches; metadata filters are applied before the result limit. `notes-cli list` exposes the filters and returns a short excerpt plus incoming and outgoing counts; `notes-cli search` exposes the bounded search.

The index stays in memory for each command or host cache. No database, committed `INDEX.md`, schema field, background service, or incremental invalidation protocol is introduced. Invalid and foreign files remain visible through existing diagnostics and are excluded from URI lookup, graph edges, and semantic queries; the existing `byId` scan lookup remains available to write validation. External relation targets remain in the relation and backlink maps even when this checkout cannot resolve them.

## Alternatives considered

- Add a SQLite or persistent search database - strongest case is faster repeated queries, but it adds lifecycle, migration, and stale-cache failure modes before the corpus size justifies them; rejected.
- Keep only `byId` and path lookup - strongest case is the smallest API, but blueprints cannot answer incoming edges or semantic filters without duplicate scanners; rejected.
- Put excerpts and backlinks into Note frontmatter - strongest case is direct reads, but derived values drift and enlarge the sealed schema; rejected.
- Do nothing / reuse - preserves the current CLI surface, but body search and graph navigation remain host-specific work; rejected.

## Consequences

One scan now supplies the minimum graph surface needed by a later blueprint adapter while retaining the existing write and validation paths. Search is intentionally substring-based and bounded; ranking is deterministic rather than relevance-model based. A future cache can be added behind the same index API only when measured scan cost requires it. Verification covers URI lookup, outgoing and incoming relation preservation, code-path filtering, excerpts, body search, and filtered result limits.
